# GitLab Vars Mode — `docs/gitlab-variables.md` 자동 생성 (하이브리드)

## 목적

GitLab → Settings → CI/CD → Variables 에 등록할 키를 **두 종류로 묶어** 출력:

1. **File Variable** (Type=File) — 비밀이 아닌 설정값 ~30개를 단일 코드 블록으로 묶어 한 번에 업로드
2. **개별 Variable** (Type=Variable + Masked) — 진짜 비밀값(PASSWORD/SECRET/TOKEN 류) 만 개별 등록

→ 등록 클릭 수 40+ → ~13 개로 감소. 비밀값은 여전히 GitLab 자동 마스킹 보존.

## 입력 소스

모두 `$REPO`(=`git rev-parse --show-toplevel`) 기준.

### 1. 코드가 실제로 참조하는 키 (check-mode 와 동일 grep)

- backend: `app/backend/src/**/*.{yml,kt}` 의 `${KEY}`, `@Value("\${KEY}")`
- frontend: `app/frontend/src/**/*.{ts,tsx}` 의 `import.meta.env.VITE_KEY`
- ai: `app/ai/**/*.py` 의 `os.getenv("KEY")` / `os.environ["KEY"]`

### 2. `infra/env/README.md` 테이블의 키

prefix 있는 형식 그대로 추출:

```bash
grep -oE '`ENV_(BASE|DEV|MASTER)(_(APP|INFRA))?_[A-Z][A-Z0-9_]+`' \
  "$REPO/infra/env/README.md" \
  | sed 's/`//g' | sort -u
```

### 3. `.gitlab-ci.yml` 의 시스템 변수

`DISCORD_WEBHOOK_URL` 등 prefix 없이 직접 쓰이는 키:

```bash
grep -oE '\$[A-Z][A-Z0-9_]+|\$\{[A-Z][A-Z0-9_]+' "$REPO/.gitlab-ci.yml" \
  | sed -E 's/^\$\{?//' \
  | grep -vE '^CI_' \
  | sort -u
```

## 분류 규칙 (3단계)

### A. 서비스 판정 (app vs infra vs system)

| 원 키 | 서비스 판정 | 생성 prefix |
|---|---|---|
| app 코드 참조 (backend + frontend + ai) | app | `ENV_<TARGET>_APP_<KEY>` |
| infra 표준 (whitelist 의 Docker 이미지 표준) | infra | `ENV_<TARGET>_INFRA_<KEY>` |
| 시스템 (`DISCORD_WEBHOOK_URL` 등) | system | 그대로 (prefix 없음) |

예외:
- whitelist.md 의 **Compose/CI 전용** 키(`ENV_DIR`, `REGISTRY`, `APP_IMAGE_TAG` 등) 는 GitLab Variables 등록 대상 아님 → 출력 제외
- Spring 표준 indirect 키(`SPRING_DATASOURCE_*`) 는 주로 `DB_*` 형태로 등록 → whitelist 참고

### B. 민감도 판정 (File 묶음 vs 개별 Masked)

`is_sensitive(key)` 매칭:

```python
import re
def is_sensitive(key: str) -> bool:
    # 끝/경계가 다음 패턴 → 개별 Masked Variable 로 등록
    return bool(re.search(
        r'(_PASSWORD|_PASS|_TOKEN|_SECRET|_WEBHOOK_URL|_DSN|_API_KEY|_SECRET_KEY|_ACCESS_KEY_ID)(_|$)',
        key
    ))
```

매칭 결과:
- ✅ sensitive: `DB_PASSWORD`, `JWT_ACCESS_SECRET`, `KAKAO_CLIENT_SECRET`, `OPENAI_API_KEY`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `GEMINI_API_KEY`, `DISCORD_WEBHOOK_URL`, ...
- ❌ not sensitive (= File 묶음): `DB_URL`, `KAKAO_CLIENT_ID`, `VITE_KAKAO_CLIENT_ID`, `RABBITMQ_GENERATE_ROUTING_KEY` (단순 `_KEY` 끝은 매칭 안 됨), ...

**왜 `_KEY` 단독 매칭 X**: `RABBITMQ_*_ROUTING_KEY` 같은 라우팅 식별자가 잘못 잡히는 것 방지. 진짜 자격증명은 `_API_KEY`, `_SECRET_KEY`, `_ACCESS_KEY_ID` 형태로 명시.

**왜 `KAKAO_CLIENT_ID` 가 비민감**: OAuth 표준상 client_id 는 redirect URL 에 평문으로 노출되는 식별자. 진짜 비밀은 `KAKAO_CLIENT_SECRET`.

### C. Protected 판정

```python
is_protected = (target == "MASTER") and is_sensitive(key)
```

master 환경의 비밀값만 Protected 플래그 추가.

## 등록 방식 — 두 종류 운영

| 종류 | 용도 | GitLab Type | Masked |
|------|------|------------|--------|
| **File Variable** | 비밀이 아닌 설정값 묶음 (~30개) | `File` | ❌ |
| **개별 Variable** | 진짜 비밀값 (PASSWORD/SECRET/API_KEY 류) | `Variable` | ✅ |

같은 키가 두 곳에 있어도 **개별 Variable 이 항상 이김** — `generate-env.sh` 가 File 내용을 base 로 깔고 개별 Variable 을 그 위에 append (last-wins). 마이그레이션 중 양쪽 공존 상태도 안전.

## 자동 분류 규칙 (env-sync)

키 끝/경계가 다음 패턴 → **Masked ✅** + 개별 Variable:
- `_PASSWORD`, `_PASS`
- `_TOKEN`
- `_API_KEY`, `_SECRET_KEY`, `_ACCESS_KEY_ID` (단순 `_KEY` 단독은 제외 — `_ROUTING_KEY` 같은 식별자 보호)
- `_SECRET`
- `_WEBHOOK_URL`
- `_DSN`

그 외 비밀이 아닌 일반 설정값 → **File Variable** 코드 블록.

`ENV_<TARGET>_<SCOPE>_ENV_FILE` 자체는 prefix 매칭 단계에서 `generate-env.sh` 가 차단 (자기 재귀 방지). 일반 `_FILE` 접미사 변수(`TLS_CERT_FILE`, `CONFIG_FILE` 등) 는 영향 없이 통과.

## File Variable 작성 시 주의 (Footguns)

| 실수 | 결과 |
|------|------|
| `KEY="value"` (값에 따옴표) | env_file 은 따옴표 안 벗김 → 값에 literal `"` 포함 |
| 줄 끝이 CRLF (Windows) | 일부 파서가 `value\r` 로 인식 → 비교/연결 실패 |
| 키 오타 (`DB_URLL=`) | 개별 변수에 같은 키가 없으면 default fallback → 조용한 버그 |
| 비밀값을 File 에 넣음 | 동작은 하지만 GitLab 마스킹 못 받음 → 로그 노출 위험 |

권장: 따옴표 X, LF 저장, 비밀은 File 에 placeholder 만 두고 진짜 값은 개별 Masked Variable.

## 체크박스 보존 및 삭제 추적

기존 `docs/gitlab-variables.md` 가 있으면:

1. 파일 파싱해서 `all_old_keys`(전체 키 목록) 와 `checked_keys`(체크된 키 목록) 두 셋 추출
   - `~~\`KEY\`~~` 형태의 삭제 대기 항목도 `old_keys` 에서 제외 (이미 처리 중인 항목)
   - File 변수의 코드 블록 안 키들도 `all_old_keys` 에 포함 (재분류 시 비교용)
2. 새로 생성할 때:
   - **기존과 동일한 키** → `[x]`/`[ ]` 상태 그대로 보존
   - **새로 추가된 키** → File 또는 개별 섹션에 `- [ ]` (미등록 상태로 시작)
   - **민감도 재분류된 키** (예: 새로 sensitive 가 됨) → 개별 섹션으로 이동, 체크박스 reset
   - **제거된 키** → 해당 섹션 말미에 삭제 대기 항목으로 추가:
     ```
     - [ ] ~~`OLD_VAR_NAME`~~ — **GitLab에서 삭제 필요** — 삭제 완료 후 체크
     ```
3. 삭제 대기 항목(`~~KEY~~`) 이 체크되면 다음 재생성 시 해당 항목 제거 (삭제 완료로 간주)

## 신규 키 시각적 구분 (File 코드 블록)

File 변수의 ```env 코드 블록 내부에서 **새로 추가된 비민감 키는 빈 줄 한 줄로 분리해 블록 말미에 모음**. 사용자가 GitLab UI 에서 File 변수를 열 때 "어떤 줄을 새로 붙여 넣어야 하는지" 즉시 식별 가능.

규칙:

1. 기존(이전 재생성에 이미 있던) 비민감 키들은 **canonical 순서** 그대로 블록 상단에 배치
2. 마지막 기존 키 다음에 **빈 줄 1개** 삽입
3. 신규 비민감 키들을 빈 줄 다음에 추가 (canonical 순서 유지)
4. 신규 키가 없으면 빈 줄도 추가하지 않음 (블록 모양 변화 X)

예시 — 기존 블록에 `STORYBOARD_IMAGE_MODEL` 과 `RABBITMQ_IMAGE_GENERATE_QUEUE` 두 개가 새로 추가된 경우:

```env
SPRING_PROFILES_ACTIVE=dev
DB_URL=jdbc:mysql://dev-mysql:3306/...
DB_USERNAME=app
... (이전 회차에 있던 키들)
AI_WORKER_REPLICAS=1

STORYBOARD_IMAGE_MODEL=gemini-2.5-flash-image
RABBITMQ_IMAGE_GENERATE_QUEUE=ai.image.generate.request.queue
```

다음 회차 재생성에서는 이 두 키도 "기존" 으로 분류되어 빈 줄 없이 정상 위치로 합쳐짐 → 블록은 다시 단일 단위.

**개별 Masked Variable 체크리스트는 분리 X**: 새 키도 같은 섹션 안에 `- [ ]` 로 추가하면 체크박스 만으로 미등록 여부가 자명하므로 빈 줄 분리 불필요.

## 실행 흐름

1. **기존 파일 파싱** (있으면) → `all_old_keys` 셋 + `checked_keys` 셋 만들기 (삭제 대기 제외)
2. **키 수집**:
   - 코드 grep 3종
   - README 테이블 파싱
   - `.gitlab-ci.yml` 시스템 변수
3. **화이트리스트 필터**: whitelist.md 의 Compose/CI 전용 키 제외
4. **prefix 확장**: 서비스 판정 결과에 따라 `ENV_<TARGET>_APP_<KEY>` / `ENV_<TARGET>_INFRA_<KEY>` 생성 (dev/master 각각)
5. **민감도 판정**: 각 키에 `is_sensitive(key)` 적용 → File 묶음 vs 개별 분류
6. **Masked / Protected 태그** 부여 (개별 변수에만)
7. **File 코드 블록 조립**:
   - 비민감 키들을 prefix 떼고 `KEY=VALUE` 형식으로 한 줄씩
   - 값은 `infra/env/README.md` 의 같은 키 설명 열에서 추출 (가능하면 literal, 사용자 채워야 할 자리는 `<...>` placeholder)
8. **체크박스 적용**:
   - 기존과 동일한 키 → `[x]`/`[ ]` 보존
   - 새 키 → `- [ ]`
   - 민감도 재분류된 키 → 새 섹션으로 이동, 미체크 시작
   - 제거된 키 → 삭제 대기 항목 추가
9. **파일 출력**: `docs/gitlab-variables.md` 덮어쓰기

## 주의사항

- **GitLab API 호출 없음** — 순수 로컬 생성. 등록 상태와 체크박스는 수동 동기.
- **체크박스 무단 수정 금지** — "**실제 등록 완료한 사람이 commit**" 규칙 유지.
- **ENV_BASE_* 판정은 수동** — 스킬은 환경별 분리만 하고 BASE 는 빈 섹션 유지. 공통값 생기면 사용자가 README 수정 후 재생성.
- **하이브리드 키(`ENV_<TARGET>_<SCOPE>_ENV_FILE`) 는 자동 생성 대상 아님** — 사용자가 GitLab UI 에 직접 등록. 스킬은 어떤 값을 코드 블록에 넣을지 안내만.
